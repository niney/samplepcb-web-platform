# partner-tracks

## Purpose [coverage: high — 14 sources]

**협력사(파트너) 트랙** = 고객 주문의 뒤편에서 도는 **관리자 ↔ 협력사 협업 축** 전체. 레거시 SmartBOM(sp-smartbom-web + samplepcb_xpse)의 두 트랙을 "레거시 설계 추종이 아니라 **돌아가는 프로세스만** 이식"해 플랫폼 척추(sp-node `/api` + sp-vue `/app/admin`·`/app/partner` + sp-php 브리지)로 재구성했다. 소스 날짜 범위는 **2026-07-29(BOM 트랙 정본 작성) ~ 2026-10-11(PCB EQ 문항형 회차·협력사 선적 완료 확인)** 이고 이 토픽의 사실은 전부 6개월 이내다(배경 자료인 레거시 통화 설계서만 2026-06-20 작성). 시간축은 넷으로 읽는다:

1. **07-29~08-02 BOM 트랙**이 문법을 세웠다 — 스냅샷 박제·서버 인가 핑퐁·역할별 워크큐·"박스에 먼저 담는" 발송 모델.
2. **08-04~08-18 PCB 트랙**이 그 자산의 7할을 재사용하며 PCB 고유 축(EQ 5단계·MD 2단·다중통화·A/S 회차·직송·스텐실)을 얹었고, **08-10~08-11 완주 여정 1~43호**가 결함 60여 건을 교정해 가드 체계를 굳혔다.
3. **08-22~09-16**은 새 상태 기계가 아니라 **통합·UX**다 — 포털 사이드바 셸 R3·협력사 보유 부품 원장·i18n·Mouser 인계·입고 스캔·관리자 메뉴 정리.
4. **09-30~10-11**은 다시 **축을 더한다** — 결제 후 부품 확인 요청(D43·D44), BOM 외화 회신·마스터딜러 중개(D45~D48), MD 의 하위 협력사 직접 관리와 관리자 대리 접속, PCB EQ 문항형 회차(D20 — AI 초안·회신서·번역), 협력사 '선적 완료' 확인. 공통 문법은 **기존 상태 기계를 포크하지 않고 원장·기록·파생으로 넓힌다**는 것이다.

정본 우선순위: [SMARTBOM_PARTNER_RFQ](../../docs/SMARTBOM_PARTNER_RFQ.md)는 **§5.1 정정이 본문보다 우선**, [PCB_PARTNER_TRACK](../../docs/PCB_PARTNER_TRACK.md)은 **§9 구현 기록이 §5 설계안보다 우선**이며 레거시 위키·문서는 신뢰하지 않는다(코드·DDL 헤더 주석 > doc > 위키).

범위와 정본:

- **BOM 트랙** — 고객 스마트 BOM 견적(`sp_bom_quote`, 정본은 [sp-node-api](sp-node-api.md)의 BOM 절)이 `reviewing`에 들어간 뒤: 협력사 RFQ(부분 행 발송·미회신 요청에 행 추가·매직링크 무로그인 회신·관리자 대리 입력·**링크 통화 회신**·MD 하위 재요청) → 3사 라이브 시세와 나란히 비교·선정 → 확정가 → 고객 주문(견적 통째 1카트행, 확정가×1.1) → 결제 확인 후 협력사 발주서(PO)·MD 하위 발주·외부공급사 카트/리스트·송금 원장 → (부품·금액·납기가 바뀌면) **결제 후 부품 확인 요청**과 차액 정산 → 선적 핑퐁(국제 6·국내 3단계)·Packing List·QR·상업송장·거래문서 → 입고 → 고객 배송 → 클레임. 정본 [SMARTBOM_PARTNER_RFQ](../../docs/SMARTBOM_PARTNER_RFQ.md)(D1~D48, §6.1~6.45).
- **PCB 트랙** — 거버 견적(`sp_order_spec`) 위에 확정가 **앞단**의 협력사 RFQ(직속·MD 2단·KRW/USD/CNY) → 선정+확정가 → 주문·입금 후 PO → **EQ 5단계**(또는 메탈마스크의 문의+좌표파일)와 그 옆의 **고객 확인 문항형 회차**(D20) → 생산 → 박스 발송(받는측 관리자/MD, 직송, Case ID 갈래, 항공/해상) → 협력사 선적 완료 확인(국제) → 입고확인 → 고객 배송 → A/S 재발주 회차 → 고객 클레임. 정본 [PCB_PARTNER_TRACK](../../docs/PCB_PARTNER_TRACK.md) §6 결정(D1~D20)·§9 구현 기록, EQ 엑셀 AI 분석의 모델·프롬프트 근거는 [PCB_EQ_AI_PROBE](../../docs/PCB_EQ_AI_PROBE.md).
- **파트너 포털** IA·셸·하위 협력사 직접 관리·관리자 대리 접속([PARTNER_PORTAL](../../docs/PARTNER_PORTAL.md)), **협력사 보유 부품 원장**([PARTNER_PARTS](../../docs/PARTNER_PARTS.md)), 포털 **i18n**([partner-i18n](../../docs/partner-i18n.md)), **발송 이력 원장**([MAIL_LOG](../../docs/MAIL_LOG.md)), 고객 주문의 **배송방법 축**([DELIVERY_METHOD](../../docs/DELIVERY_METHOD.md)), **사내 서비스 BOM API**([BOM_SERVICE_API](../../docs/BOM_SERVICE_API.md)), 회수한 레거시 자료([legacy-smartbom](../../docs/legacy-smartbom/README.md) — "결제 통화는 멤버가 아니라 링크의 속성"이라는 통화 규칙의 원형은 [링크별 결제 통화 재설계](../../docs/legacy-smartbom/currency-link-model-redesign.md)).

역할 다섯이 축이다:

- **관리자** — 검토·배정·선정·확정가·발주·EQ 승인·입고확인·송금·삭제. "만능 대행"(D11)으로 협력사 몫도 대신 밀고 `byRole='ADMIN'`이 박제된다. 10-09부터는 **대리 접속**으로 그 조직의 포털 자체를 쓴다(무계정·정지 조직 포함).
- **협력사** — 회신·발주 확인·EQ 올림·추가 EQ 요청·생산·발송·선적 완료 확인·A/S 회신·재고표 업로드. 포털 계정이 없어도 매직링크(RFQ)와 관리자 대행으로 트랙이 끝까지 간다(여정 12호).
- **마스터딜러(MD)** — 위로는 협력사, 아래로는 관리자. 하위 배정·마진·중계 물류·관전/대행(`byRole='MASTER_DEALER'`). 역할의 정본은 `sp_partner.isMasterDealer` 표시(10-10)이고 포털에서 하위를 직접 등록·수정·삭제한다. BOM 에서는 품목별 하위 선정·마진·하위 발주(D46·D47).
- **고객** — 주문·EQ 고객 확인(문항별 회신)·부품 확인 요청 회신·추가결제·진행 조회·A/S 접수. 협력사명·발주가는 끝까지 비노출(공급망 차단, 여정 43호).
- **공급사**(DigiKey·Mouser·UniKeyIC) — 로그인 주체 없는 API 조직. RFQ 행으로 물질화하지 않고 구매 조건 원장에서 파생(D6), 발주는 카트/리스트까지만(D20).

화면·라우트 상세는 [sp-vue-web](sp-vue-web.md)·[sp-node-api](sp-node-api.md), 스키마는 [api-contract](api-contract.md), 하네스는 [testing](testing.md)이 맡고 이 토픽은 **업무 흐름·상태 기계·가드·역할·돈·문서**의 정본 요약만 담는다.

## Architecture [coverage: high — 16 sources]

**조직 모델 — 계정·조직·자동화 3축 분리**(D4·D5):

- `sp_partner`(type `partner|supplier|house`, `capabilities ["bom_rfq","pcb_rfq","part_sale"]`, status `pending|approved|suspended`, `country` ISO2 = 발송 출발국, `defaultCurrency`/`inputCurrency`, 사업자정보 6칸, **`isMasterDealer`** 역할 표시·**`ownerPartnerId`** MD 가 등록한 하위의 소유) + `sp_partner_member`(g5 계정 연결 — 가짜 회원 없음, 1계정=1조직 가드) + `sp_partner_relation`(MD↔하위, **링크 결제통화** 박제, 2단 강제·다중 상위 허용) + `sp_partner_invite`(본인 계정 연결용 1회용 초대).
- 로그인 능력=멤버 존재, API 자동화 능력=`supplierCode` 존재 — 조합으로 일반 협력사/순수 공급사/하이브리드/자사 house가 표현된다.
- 인증은 `requirePartner`([auth.ts](../../samplepcb-web-mono-app/apps/api/src/plugins/auth.ts))가 **매 요청 DB 판정**(JWT에 조직 클레임 없음 — 정지 즉시 403, 토큰 재발급 불필요), capability는 라우트가 다시 확인한다 — [server-single-truth](../concepts/server-single-truth.md). 관리자 **대리 접속**은 그누보드 세션 전환이 아니라 관리자 토큰+헤더 `x-sp-act-as-partner` 하나이고, `requirePartner`·`/partner/access` 두 곳이 같은 함수([partner-act-as.ts](../../samplepcb-web-mono-app/apps/api/src/lib/partner-act-as.ts))로 판정한다.
- 포털 진입은 `GET /api/partner/access`가 `tracks {bom,pcb,parts}`+`canManageChildren`으로 파생([partner-access.ts](../../samplepcb-web-mono-app/apps/api/src/routes/partner-access.ts)), PHP 헤더 링크는 [sp_partner.extend.php](../../samplepcb-web/extend/sp_partner.extend.php)가 같은 기준(멤버 ∧ approved)으로 직접 SELECT — [admin-vue-consume-php](../concepts/admin-vue-consume-php.md).

**하위 협력사 직접 관리·MD 지정·대리 접속**(10-09~10-10, [PARTNER_PORTAL](../../docs/PARTNER_PORTAL.md) §5.1~5.2):

- **MD 가 포털에서 하위를 직접 등록·수정·삭제**(`/partner/children`) — 등록은 자동 승인(사후 감독: 운영자 통지 `partner_child_registered`·'마스터딜러 등록' 배지·중복 의심), **회원은 만들지 않고** 필요하면 초대(64hex·14일, 받은 사람이 자기 계정으로 수락). 수정·삭제·초대는 내가 등록한 조직에만(`NOT_OWNED`), 삭제는 이력이 없을 때만 진짜 삭제이고 있으면 같은 버튼이 '사용 중지'로 수렴, 진행 중이면 `RELATION_ACTIVE`(PCB 견적·발주 + BOM 의 회신 왕복 중 견적요청·수령 전 하위 발주를 함께 센다). 하위마다 '맡길 일'(`pcb_rfq`·`bom_rfq`)은 내 견적 트랙 안에서만(`TRACK_NOT_ALLOWED`).
- **마스터딜러 지정** — 종전 '하위 링크가 있으면 MD' 파생을 `isMasterDealer` 표시로 바꿨다(관리자 체크·관리자의 하위 연결·포털 첫 하위 등록 셋이 켠다. 끄기는 관리자만·하위 0일 때만 `HAS_CHILDREN`, 표시된 조직은 하위가 될 수 없다 `CHILD_IS_MD`). 실제 위임의 근거는 여전히 소속 링크+발주별 `fulfillmentMode`. 첫 하위 등록(=역할 전환)의 `PARENT_HAS_ACTIVE_POS` 는 박제 이후 기술 가드가 아니라 **정책**이라 관리자만 `force`+`forceReason`(링크 `forceNote`·`createdBy`)으로 넘는다.
- **관리자 대리 접속** — 파트너 관리 [포털로 보기] → `/app/partner?actAs=<조직 id>`(탭 단위 sessionStorage, 붉은 띠). 읽기·쓰기 모두 그 조직 범위로 되고 쓰기 요청은 전부 `sp_partner_act_log` 에 남는다. 이력의 주체는 D11 표기 그대로다(EQ `byRole=ADMIN`, 첨부 `uploadedBy=ADMIN`, 박스 `actorType=ADMIN`). BOM MD 중개의 '관리자 전권'도 전용 화면이 아니라 이 대리 접속이다(D46-9·D47-7).

**관리자 콘솔** = 모듈 스위처 3모듈(통합 관리 / 스마트 BOM / PCB 협력 — 모듈 간 화면 공유 금지 D9, 컴포넌트 재사용만) × **역할별 워크큐**(견적/주문·결제/발주/[송금]/선적·배송/A·S·클레임) → 단일 **Case 상세** 척추:

- 첫 탭=그 역할의 **대기 큐**, 배지="지금 움직여야 하는 수"+진행 중 내 차례 합산(D12). 이관분 `_legacy`는 대기 큐에서만 제외(재촉 목록 330·195건이 눌러앉던 실측).
- Case 상세는 `?from=quotes|orders|pos|logistics` 로 무관 섹션을 한 줄 접힘 바로(스크롤·강조는 제거).
- 파트너 기준정보는 2026-08-06부터 통합 관리 `/admin/partners`(BOM·PCB·부품 판매가 공유하는 조직 정본).
- 삭제는 2단계 레이어(프리뷰 SHA-256 토큰 → `STALE_PREVIEW`) + `sp_delete_audit` 공용 감사(subjectType) + `audited|reset` 모드. PCB는 관리자 체크 하나로 차단 전면 해제(D14), 고객 경로는 `PARTNER_TRACK_ACTIVE` 불변.

**포털**(`/app/partner`, [PARTNER_PORTAL](../../docs/PARTNER_PORTAL.md)):

- 리졸버 `PartnerEntry`(트랙 0 안내 / 1 그 모듈 / 2 `localStorage sp.partnerModule` 기억) → 모듈 홈(오늘 할 일 카드 4장: 회신할 견적·확인할/진행할 발주·📦 보낼 물건·진행 중 발송).
- **R3 사이드바 셸**(관리자 `AdminLayout` 동형, `partner/menu.ts`, 배지는 홈 카드와 같은 쿼리 캐시 `usePartnerWork`, 본문 최대 1440px, `PartnerPageHeader` 통일, 모듈 색 BOM indigo/PCB teal/공통 amber) + 워크큐 목록 4화면(`bom|pcb/rfqs·pos`, `?tab=`).
- **공통 영역**(수금 현황 `tracks.pcb`·보유 부품 `tracks.parts`·하위 협력사 `canManageChildren`) — 모듈에 억지 배속하지 않는다. 초대 수락 `/partner-invite/:token` 은 셸 밖.
- 발송은 **[📦 보내기] 두 칸 보드**(좌 선반 ↔ 우 박스, "발송 누르기 전엔 자유", 대표 개념 은닉, 마지막 꺼내기=박스 소멸) — 레거시 3층 선적 그룹 보드 대신 **발송 시점에 묶는다**(§6.10→§6.11). 협력사 관점 상태 번역 `partnerPoDisplayStatus`('마감' 단어 소거). 10-11부터 한국어 표시문은 `선적`으로 통일됐다(메뉴 '선적 관리'·'선적 완료 내역', 국내 택배만 '배송') — i18n 키·영어·중국어는 그대로.
- i18n은 `PartnerLayout` 범위의 `pt()` 주입(ko/en/zh-Hans, `sp.partner.locale`) — 전역 vue-i18n·메일·매직링크·PHP는 범위 밖.

**BOM 상태 기계** — `quote.status draft→requested→reviewing→answered→closed`는 불변이고 그 아래에 하위 계층이 돈다(D10 상태 계층 분리):

- `BOM_RFQ_STATUS requested→quoted→closed` — diff 발송: 빠진 협력사 중 **미회신만 회수**, quoted 보존(D32-1). 0곳 발송=미회신 전부 회수. 회신 3경로(포털·매직링크·대리)는 `saveRfqReply` 코어 하나. 10-10 개정: `requested` 인 요청에 한해 `expandPartnerIds` 로 행을 **합집합**으로 더한다(줄이지 않는다, 회신한 요청이 섞이면 409 `RFQ_ALREADY_REPLIED` 로 트랜잭션째 되돌림, 메일 `bom_rfq_scope_added`). 고객 취소도 같은 트랜잭션에서 RFQ 를 닫는다(10-05 — 종전엔 관리자 PATCH 만 닫아 취소된 견적에 회신이 저장됐다).
- PO `issued→confirmed→closed`(D18 — 발주서=Case×협력사 1건 박제 문서, **결제 확인(od isPaid) 후**, VAT 별도, `issued`만 삭제). 공급사 PO는 관리자 [구매 완료 처리]로만 confirmed(D33).
- **MD 중개(D46·D47)** — 하위 재요청은 같은 문서 종류다(`sp_bom_rfq.parentPartnerId=MD`, 직접 요청 parent=0 에서만 열리는 2단, 통화는 MD↔하위 링크 통화). 품목별 선정은 **회신 저장의 일부**: 회신 품목에 `childRfqId`+`marginRate` 를 실으면 서버가 `하위가×환율×(1+마진%)` 를 산출하고 근거 5컬럼을 남긴다(클라이언트 단가는 무시, 환율은 고른 순간 굳어 마진만 고치면 유지, 하위가 재회신하면 `childSelection.stale`). 관리자가 고르는 것은 parent=0 회신뿐. 하위 발주는 **별도 문서** `sp_bom_md_po`(`issued→confirmed→shipped→received`, 누가 무엇을 누르나는 계약 `bomMdPoActionsFor` 한 곳, 계정 없는 하위는 MD 가 대행).
- **결제 후 부품 확인 요청(D43·D44)** — 구간은 결제 확인 뒤~고객 배송 전(결제 전은 D25/D26 품목 교체, 배송 뒤는 D37 클레임). 요청 1건=Case×문제 품목 N(`requested→answered→resolved|canceled`, `version` 낙관적 잠금, 품목당 열린 이슈 1건 `activeKey`), 유형 11(질문 9+알림 2 — 알림은 만들자마자 종결), 근거·선택지는 요청 시점 박제([snapshot-freeze](../concepts/snapshot-freeze.md)), 무응답은 자동 결정 없이 관리자 **대리 회신**. 적용은 '결제 후 변경'(그 행만 갱신, 확정가·견적 상태 불변) 또는 행 `fulfillment=customer_supply|backorder`, 정산은 요청 단위 순액 1건(추가결제=앵커 `sp-bom-extra` 별도 주문의 lazy 확인, 환불=원 행 감액→기록). 열린 이슈는 발주서 생성과 공급사 발주서의 구매 완료 처리(둘 다 409 `CONFIRM_PENDING`)·배송 게이트·고객 진행('조달 중' 캡)을 붙잡는다.
- 선적 `INTL preparing→requested→shipped→arrived→customs→done / DOMESTIC preparing→shipping→delivered` — 모드는 협력사 `country`로 서버가 생성 시 박제(D28). 주체 사전 `BOM_SHIPMENT_ACTORS`: 국제는 협력사가 **선적 요청 한 번**, 이후 선적·도착·통관·완료 전부 관리자; 국내 종점은 관리자 [입고 확인] 전용 API.
- 12단계 **파생** 타임라인(`smartbomStepOf`, 저장 안 함 — [lazy-derived-state](../concepts/lazy-derived-state.md)). 주문·결제 상태는 `ctId→g5_shop_cart→g5_shop_order` 조인 파생이며 g5 미러 컬럼을 두지 않는다.

**PCB 상태 기계** — 앵커는 `it_id`가 아니라 **`sp_order_spec.id`**(specId):

- RFQ `requested|quoted|selected|unselected`(UK `specId+partnerId+parentPartnerId+reorderRound`). 담기지 않은 active 스펙 전체에 시작 가능, 진행 중 주문은 **원가 소싱 모드**(D10). 선정=확정가 등록 **앞단**(담김/주문이면 409 — 레거시 소급 전파 폐기, [snapshot-freeze](../concepts/snapshot-freeze.md)).
- 주문·입금 → PO `issued→eq_requested→eq_done→producing→produced`. `PCB_EQ_FORWARD/REVERT` 사전이 라벨·서버 검증의 단일 정본, EQ 승인은 **관리자만**(D3), 첨부 eq 선택/working 권장(D19)·승인요청 뒤 `EQ_LOCKED`, 반려↔요청취소는 **note 유무**로만 갈리고 판정은 `isPcbEqRejectionEvent` 하나. 10-11: 승인 뒤 협력사 **[추가 EQ 요청]**(`PCB_EQ_REOPEN` — RECEIVER, `eq_done→issued`, 사유 필수·생산 시작 전까지·스텐실은 `NOT_EQ_TRACK`)이 되돌리기 사전과 다른 축으로 생겼고, 그래서 `issued` 가 '아직 안 낸 상태'가 아니게 돼 **굳은 파일**(`isPcbEqFileRecord` — 올린 뒤 승인된 적 있거나 고객에게 나간 회차의 근거)은 삭제 409 `FILE_RECORD_LOCKED`. 경계는 `lastPcbEqReworkBoundary`(반려 또는 추가 EQ 요청 중 최근 하나, 서로 배타).
- **메탈마스크 트랙**은 status를 포크하지 않고 `resolvePcbPoTrack(category) → 'eq'|'stencil'`로 라벨·게이트만 가른다(좌표파일 필수·문의 선택·확인 뒤 통보 없는 고객 열람).
- **고객 확인 = 문항형 회차(D20)** — 발주 상태는 그대로 두고 D16 원장 `sp_pcb_eq_review` 를 회차로 넓혔다: `format message|items`, 문항형은 `draft`(고객 응답·배지·목록에 절대 안 실림)→`requested`→`answered`|`canceled`, 열린 회차는 발주서당 1개(`ALREADY_OPEN`), `version` 낙관적 잠금. 문항=유형·한국어 질문·공장 원문·선택지(**기호는 공장 원문 A/B/C 그대로**, `requiresComment`·`recommended`)·그림(공개는 문항별 `shared`), 개정은 `fromPrevious` 로 `same|changed|new` 연결, 관리자 대리 회신(채널·근거 필수). 종결(`eq_done`)은 여전히 관리자이고 **승인이 같은 트랜잭션에서 미전달 회신을 협력사에 전달**한다. 협력사는 포털 '고객 회신' 카드·회신서 xlsx 로 읽고, 고객 의견·관리자가 쓴 사유는 저장 뒤 한 번 번역해 원문과 병기한다(`answerCommentI18n`·`eqHistory[].noteI18n`).
- **AI 초안(D20 P2)** — 협력사(또는 대행)가 [승인요청]을 누르는 순간 `sp_ai_job`(useCase `pcb.eq-parse`, targetType `pcb_po`)이 최신 EQ 첨부를 분석해 **초안까지만** 만든다(고객 발송은 관리자 검토 뒤). `analyzeEqFile`: 결정적 추출(.xls/.xlsx/.zip 셀·병합·그림) → LLM 구조화·번역(kimi-k3·think low·`eq-parse-v3`) → 결정적 사후 검사가 문항별 `aiFlags`(`structure|translation|figure`)를 붙인다. 개정 연결은 LLM 이 아니라 결정적 대조(원문 일치 먼저, 그다음 번호), 실패(`unsupported_file|unreadable|no_items|llm_failed`)는 화면 표시만. 잡에는 LLM 원출력만 저장해 재적용은 모델 호출 없이 재현한다 — [in-memory-async-jobs](../concepts/in-memory-async-jobs.md).
- 선적은 BOM 코드사전·transport 사전을 **재사용**하되 `receiverKind admin|md`·`destinationCountry`(직송 KR/CN/VN)·**박스 contextKey `받는측:받는조직:직송지:회차`**(같은 컨텍스트 preparing 박스에 합류 — 고객·스펙 축은 없어 다른 고객 물건이 한 상자에 섞이는 것이 정상)·**출고 게이팅**(MD는 하위 입고확인 전 상위 출고 `OUTBOUND_BLOCKED`). 10-11: 국제 발송에서 받는 쪽이 '선적'을 진행하면 협력사가 **[선적 완료]**로 확인한다 — 상태가 아니라 기록(`shipConfirmedAt/By`), 판정은 계약 `pcbShipConfirmPending`·`pcbShipmentSenderDone`, 관리자 진행은 막지 않는다(미확인 채 국내도착으로 넘어가면 뒤늦은 확인은 `SHIP_CONFIRM_UNAVAILABLE`, '선적'을 되돌리면 확인도 비움). Case ID 갈래의 관리자 선적 줄은 스트립 3칸(인보이스 선택 → 운송서류 필수=**붙인 서류가 곧 운송수단** → Case ID·운송장 입력)으로 순차화됐다.
- 입고확인 `receivedAt`이 다음 일을 여는 열쇠(국내는 `RECEIVE_REQUIRED`로 상태까지 함께 닫힘) → 고객 배송 큐(판정=관리자 수신 선적의 입고 신호, 직송은 [직송 완료]). od 상태는 **무접촉**(D6).
- **MD 2단**: RFQ 하위 배정→하위 회신→마진%로 상위 회신가 서버 계산(`mdAmount=하위금액×환율×(1+마진%)`, 최종 1회 HALF_UP, `source_*` 박제) → 발주 건별 `fulfillmentMode self|delegated` 박제(08-18) → 위임이면 하위 발주 후 상위 상태 미러·MD는 RECEIVER fallback. 산식은 계약 `pcbMdQuoteAmount` 를 서버 박제와 포털 미리보기가 같이 쓰고(10-11), 하위 선정으로 만든 회신도 직접 회신과 같은 `notifyPcbRfqReplied` 로 관리자에게 통지된다.
- **A/S**: 얇은 접수 헤더 `sp_pcb_as_case`(draft→submitted→accepted|rejected→proceeded) + proceed 시 회차 MAX+1 채번·원발주 복사(납기는 비움)로 회차 발주서가 같은 EQ·선적 파이프를 탄다. 회차 하위 발주는 원회차 조건 복사(childRfqId 불요).

**가드 체계(잠김→정리→열림)** — 재작업 검증 1~3단계(08-10)와 여정들이 세운 앱 가드(스키마 무변경). 검사 순서가 곧 명세다(발주 취소는 `NOT_ISSUED`를 `IN_SHIPMENT`보다 먼저 본다):

| 코드 | 잠김 | 정리(출구) |
|---|---|---|
| `PO_ISSUED` | 발주 있으면 선정 해제·사양 수정 불가 | 발주 취소 |
| `RFQ_NOT_SELECTED` | 미선정 회신을 근거로 발주 불가(수동 발주 API는 유지) | 선정 |
| `HAS_REMITTANCE` | 송금 기록 있으면 발주 취소 불가 | 원장 삭제 라우트(leaf-first) |
| `IN_SHIPMENT` | 담긴 발주는 취소·직송지 변경 불가 | 박스에서 detach |
| `DOC_LOCKED` | preparing 아니면 첨부 삭제 불가 | 되돌리기(재진입은 Invoice 재요구) |

**돈**:

- PCB: 한 링크=한 결제통화(관리자↔협력사·MD는 조직 `defaultCurrency`, MD↔하위는 관계 `settlementCurrency`), 각 당사자는 자기 통화만 보고 환율은 **변환점에서만** 박제(선정 시 `krwAmount`, 회신 바디엔 환율 키 자체가 없음, 생략하면 수출입은행 당일 tts, KRW는 null).
- **송금은 상태가 아니라 원장**(`sp_pcb_remittance`, D15): 잔액=발주가−송금 합계, `unpaid|partial|paid|over`, 송금 환율은 발주 환율과 별도라 원장 KRW 실합≠발주 회계=환차, 무상 A/S 회차와 MD 하위 발주는 집계 제외, 결제조건별 예정일 `remittanceDueOn`, 완납 통지는 발주서당 1회 `pcb_remit_settled`.
- **과입금**은 `od_refund_price`에 환불 사실만 기록(코어 미수 산식에 이미 포함되어 적는 순간 0으로 닫힘, 실행은 사람).
- BOM: RFQ 통화는 **링크 통화**(D45, 10-09 — 종전 KRW 고정 D7): 배정 순간 `sp_bom_rfq.currency` 에 박제(직접 트랙=조직 `defaultCurrency`, MD↔하위=관계 `settlementCurrency`). 환율은 PCB 처럼 선정 때 행마다가 아니라 **견적 단위로 통화별 한 번 굳힌다**(`partnerFxRates` — 품목 수십 줄이 공급사 달러 가격과 한 표에서 비교되므로, 관리자 직접 입력 `partner-fx` 가능). 선정 박제는 언제나 원화이고 원본은 `selectedOffer.sourcePrice`(공급망 정보라 고객 응답에서 지운다). 발주서 정본은 결제통화, 원화는 **발행일 실제 환율**의 회계값이며 보는 쪽에 따라 통화가 갈린다(`PoMoneyAudience` — 협력사는 결제통화만). 환율은 세 겹이다: 고객가(견적 고정+마진) → 장부(발행일) → 지급(송금일).
- BOM 송금도 원장(`sp_bom_remittance`, D48 — PCB D15 와 같은 모양): 송금 통화=발주 통화 강제, 지급할 금액=부족 신고분을 뺀 실제 공급 금액, 환차=실제 원화−장부 환율 원화, 초과 지급은 막지 않고 `over` 로 드러내며 정정은 삭제 뒤 다시 적는다. 협력사에게는 받은 금액·잔액만. 확인 요청의 차액은 Case 단위 정산 원장 `sp_bom_settlement`(FK 없음 — Case 가 지워져도 돈 기록은 남는다).
- BOM 공통: 실효 회신수량 `stampOrderQty(replyQty ?? orderQty, moq)` 단일 공식(§6.38), 카트 금액 `round(confirmedTotal×1.1)`, 협력사 PO VAT 별도, 국내 거래문서 공급가/VAT 분리, 부분취소는 영카트 원칙으로 `od_cancel_price`·미수·세액 재계산(D30). 대체 발주 단가 차이는 내부 조달 차이(D31-4 — 결제 후 고객 금액 소급 변경 금지. 단 **고객이 답한 확인 요청 결과에 한해** 금액이 바뀐다, D43-11 개정).

**문서**:

- BOM: 고객 견적서(브라우저 인쇄만 D12, `CASE-B-YYMMDD-{id}` 표시 채번, 확정 전 "가안") · 협력사 견적서 `PQT-SPB-{poId}`·거래명세서 `STMT-SPB-{shipmentId}-R{rev}`(국내 전용, 발행 시 `quotationData` 박제 D27) · Commercial Invoice(국제 전용, `invoiceData` 편집본+`fresh` 재조립, PDF 자동 첨부+XLSX 다운로드 D23, 묶음이면 소속 PO 전체) · Packing List+부품 QR(`sp_bom_part_package`, 실물 취급 단위 1개=QR 1개, 최초 발송 전 필수 D24) · 공급사 가져오기 csv.

## Gotchas [coverage: high — 13 sources]

- ⚠ **날짜 전용 필드는 KST 자정 앵커** — `iso.slice(0,10)` 은 하루 앞당긴다(납기가 저장마다 하루씩 밀린 실사고). `fmtKstDate/kstDateInput/kstToday/kstDateStr` 만. 단 `shipDate`처럼 UTC 자정에 앵커한 값은 손대지 않는다.
- ⚠ **`z.coerce.boolean`은 `'false'`도 truthy**(invoice `fresh` 저장본이 늘 덮이던 결함) — 쿼리 불리언은 `z.enum`.
- ⚠ **워크큐 기본 탭 함정**: `/admin/pcb/pos` 기본 탭은 '발주 대기'(발주서 없는 건), `/pcb/orders`는 '입금 대기' — 진행 중 건을 찾으려면 탭 이동+검색. RFQ·발주 큐의 기본 대기 탭엔 검색창이 없다. 없는 포털 URL은 흰 화면(404가 결함처럼 보인다).
- ⚠ **협력 트랙은 od를 게이트하지 않는다** — 취소 판정은 헤더+**줄 `ct_status`** 둘 다, 부분 취소는 od가 '입금'인 채로 줄만 취소된다. 주문 취소의 정식 경로는 `PATCH /orders/:odId/items/status`(force-status enum에 '취소' 없음). 되돌리기 `'주문'`만 취소류 포함(un-cancel+재고 복원 — 모든 e2e 정리가 기대는 근거, 여정 26호).
- ⚠ **반려 vs 요청취소는 같은 전이** `eq_requested→issued` — note 유무로만 갈린다. 되돌리기에 note를 넣으면 넷이 동시에 거짓말한다. 사유가 예약어 '되돌리기'면 409.
- ⚠ **계약 키 오독 3종**: 회신 기한은 `dueOn`(`dueDate` 아님 — 전 여정이 기한을 저장하지 못했던 오타), 고객 EQ 결정 enum은 `approve|reject`, 반려 사유는 `note`. `PATCH …/spec`은 **전체 교체**(부분 병합 아님).
- ⚠ **매직링크**: 저장형 토큰이라 재발급이 곧 회수 — 재배정 후 옛 메일 링크는 무효이니 [링크 복사]로 새 링크를 전달해야 한다. 만료 404·정지 409로 응답이 갈리는 것이 의도. 같은 견적·같은 협력사에 RFQ 재발송은 중복이라 시도조차 없다(발송 경로를 여러 번 태우려면 견적을 나눠라 — BOM 은 10-10부터 미회신 요청에 한해 행 추가가 된다).
- ⚠ **환율은 회신이 아니라 선정에서 굳는다**; 발주 뒤에는 조직 통화를 바꿔도 박제 불변. 외화 송금은 오늘 날짜만 자동 환율, 과거·미래일은 명시 필수(`EXCHANGE_RATE_REQUIRED`). 송금 바디는 `remittedOn`이고 `currency`를 받지 않는다(발주 통화 강제). `krwPoAmount ≠ krwPaidAmount + krwBalance`가 **정상**(환차).
- ⚠ **BOM RFQ 통화는 10-09부터 링크 통화**(종전 "해외 협력사도 KRW 로 회신"은 낡았다) — 반영 전에 보낸 견적요청은 KRW 로 박제돼 그대로이고, 운영 반영 뒤 **새로 보내는** 요청부터 조직 `defaultCurrency` 를 따르니 해외 협력사의 통화 값이 실제 결제통화와 맞는지 먼저 확인할 것. 환율 세 겹(고객가 고정+마진·장부 발행일·지급 송금일)을 섞지 말 것 — 여정 실측에서 같은 발주의 고객가 환율 1,403.48 과 장부 환율 1,352.59 가 다른 것이 정상이다. 환율 없는 외화 회신은 비교 후보에서 빠지고 선정은 409. 협력사 후보(보유 부품)는 가격이 없어 담긴 행은 `lineTotalKrw=null`이며 주문 게이트는 라인이 아니라 관리자 확정가다. 금액은 `ct_price`가 아니라 `io_price`, 템플릿 상품 `sp-bom-parts`, 정리는 `io_id='bom-{quoteId}'`로.
- ⚠ **Mouser API 카트≠웹 현재 장바구니**('저장한 장바구니'), 하루쯤 뒤 비어 있었고 `GET /cart`는 없는 키에도 200+빈 카트 — "빈 카트"는 존재 증명이 아니다. DigiKey Barcoding은 2-legged 401, 앱 Redirect URI는 하나(로컬/운영 환경별 연결). `SubmitOrder` 실주문은 사용자 결정 없이 켜지 않는다.
- ⚠ **대용량 JSON·트랜잭션**: `previewJson`에 엔진 결과 원문(12,175행=6.36MB)을 넣으면 MySQL 패킷 한도에서 연결이 끊긴다(표본 200행만, 커밋은 보관 원본 재실행). 후보 대량 저장은 20건 배치, 대량 삭제는 무tx 청크. 카탈로그 투영 동시 반영은 갭 락 교착 → `withWriteRetry`. 협력사 offer는 원장 FK가 없어 조직 삭제 시 `purgeOrphanPartnerOffers` 필요.
- ⚠ **Fastify 훅을 동기 `void`로 두면 요청이 영구 hang**(tsc·eslint 통과) — `Promise<void>`. `/api/svc` nginx allow는 2026-08-27 기준 미설정. `SVC_BOM_MB_ID` 회원은 ID 선점용으로 만들 것.
- ⚠ **완납 통지 레이스는 프로세스 내 직렬화뿐**(다중 인스턴스는 열림 — 원자 claim 컬럼은 이월). MD 경유 EQ 결정 메일의 MD 사본 여부는 정책 대기. `loadAdminPcbPoWorkItems`는 전건 로드+N+1(PO가 쌓이면 SQL 페이지네이션으로).
- ⚠ **sp-php 쓰기 브리지 함정**: `get_token()`은 문자열만 반환(hidden input으로 감싸야 제출이 된다), `check_token()`은 실패 시 자체 alert라 `sp_pcb_check_token()` 복제본 사용(코어 변경 시 동기), CSS 고치면 `G5_CSS_VER` 올릴 것, 주문 상세 카드 우측 열에 문장을 넣을 땐 폭을 묶어라(사양 열 0px 붕괴 2회). 배송 처리 모달의 방법 셀렉트로 force-status 우회는 끝났지만 코어 관례상 이 경로는 고객 알림 미발송.
- ⚠ **sp-php 브리지의 자유 입력은 `$_POST` 를 직접 읽지 말 것** — 그누보드 `common.php` 가 `$_POST`·`$_GET`·`$_COOKIE` 전체에 `sql_escape_string`(=`addslashes`)을 걸어, JSON 으로 sp-node 에 넘기면 `it's` 가 `it\'s` 로 저장된다(고객 화면은 `get_text()` 가 `\'` 만 되돌려 오래 안 드러났다). `sp_bridge_text`/`sp_bridge_text_map` 으로. 로컬 DB 오염은 0건, **운영 DB 는 미조사**이고 복구는 수정 배포 시각 이전 행에 한정해야 한다. 브라우저 폼은 줄바꿈을 CRLF 로 보낸다(정규화 안 함).
- ⚠ **EQ 의 '차'가 셋이다** — A/S 재발주 회차·EQ 요청 회차(`summarizePcbEqRounds`, 포털 타임라인과 같은 번호)·고객 확인 회차(문항을 보낸 횟수). 고객에게 묻지 않고 반려·승인한 요청이 있으면 뒤의 둘이 어긋난다. 고객 확인 회차 번호는 저장하지 않는 파생이고 **발주서별로** 세야 한다(목록 전체로 세어 "5차 확인"이 뜨던 P1 결함), 안 나간 채 닫힌 초안은 번호를 차지하지 않는다. 발주 행 요약 `eqReview` 는 '이번 승인요청 뒤 회차'만이라 돌아온 직후엔 지난 회차의 답이다(시간 창으로 가를 것). 최신 회차의 결말은 이력이 아니라 발주 상태가 정본(이관분은 이력이 비어 있다).
- ⚠ **`eqHistory` 를 뒤늦게 다시 쓰는 일**(사유 번역): 모델을 기다리는 사이 협력사가 재요청하면 이력이 늘어나 있다 — 읽어 둔 배열로 덮지 말고 행을 잠근 채 다시 읽어 사건을 찾아 붙인다. 전이(`appendEq`)가 이력을 파싱해 다시 쓰므로 `parseEqHistory` 가 `noteI18n` 을 실어 날라야 다음 전이에 번역이 사라지지 않는다. 자동 번역은 **비어 있는** 칸에만 쓴다(관리자가 적은 번역을 늦게 온 AI 가 덮지 않게).
- ⚠ **EQ AI 운영·검증**: 유스케이스는 기본 꺼짐이고 번역도 같은 스위치를 쓴다. 서버 재시작으로 끊긴 잡은 재개하지 않는다(실패로 보이고 [AI 다시 분석]). SheetJS 는 npm 0.18.5(CVE) 금지·CDN tarball 0.20.3. LLM `format` 은 강제되지 않으니 받은 뒤 `coerceEqDraft`+계약 검증이 필수, 번역은 원문 숫자 토큰이 그대로 있는지 결정적으로 검사해 걸리면 버린다(틀린 번역보다 원문만이 낫다). e2e 의 AI 스펙 두 본은 **한 vitest 실행에 묶을 것**(둘 다 전역 설정을 켰다 끈다 — 따로 동시에 돌려 원복이 어긋난 일이 두 번), 로컬에서 켜 둔 채 돌리면 고객 회신이 있는 스펙마다 실제 번역 호출이 한 번 나간다.
- ⚠ **D43 확인 요청**: 환불을 금액 칸에 직접 쓰면 `get_order_info` 가 취소 금액을 줄 상태로 다시 계산해 지워진다 — 원 BOM 카트행 `io_price` 감액으로. 고객 차례 배지 모수(확인 대기+**결제할** 추가결제, 무통장 주문서를 이미 냈으면 제외)는 PHP DB count 와 sp-node `openCount` 가 같아야 한다(여정 22호가 대조). 보류 품목은 발주서가 없어 진행 파생이 '입고 완료'를 띄우던 실측 → hold 캡. 운영은 `smartbom:seed-extra-anchor` 1회.
- ⚠ **MD·대리 접속**: BOM 하위 선정의 참조는 회신 행이 아니라 하위의 견적요청 문서다(재회신하면 행 id 가 바뀐다). 매직링크·관리자 대리 입력은 `childRfqId` 를 모르는 경로라 단가를 그대로 저장하면 근거를 물려받고 고치면 직접 회신이 된다. 미회신 MD 요청을 회수하면 하위 재요청도 (회신이 와 있어도) 함께 지워진다. 대리 접속 기록에서 A/S 첨부만은 `PARTNER` 그대로다(그 값은 주체가 아니라 자료 구분). 소유 조직은 관리자 PCB 배정 모달 후보(`origin=admin`)에서 빠지지만 서버가 배정을 거절하지는 않는다.
