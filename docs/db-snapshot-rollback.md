# DB 스냅샷과 원복

개발의뢰 프로토타입을 운영에서 사용한 뒤 **이전 코드와 배포 전 DB로 돌아가는 방법**이다. 기능용 `.env` 설정은 없다. 기존 `DATABASE_URL`을 사용한다.

## 평소 실행·배포

- 개발: 모노레포에서 `pnpm dev`. API 기동 전에 미적용 migration이 있으면 스냅샷 → `prisma migrate deploy` → 서버 시작 순서로 진행한다.
- 운영: `./deploy.sh 5`(전체) 또는 `./deploy.sh 2`(API+DB). 매번 배포 전 DB 스냅샷을 남기고 미적용 migration만 실행한다.
- 개발 서버는 이미 적용된 상태에서 백업과 DDL을 반복하지 않는다. 필요한 경우 Prisma 클라이언트 생성도 자동 처리한다. 동시에 실행된 DB 준비는 MySQL advisory lock으로 직렬화한다.
- `prisma migrate reset`과 공유 DB의 `prisma migrate dev`는 사용하지 않는다.

백업 기본 위치는 Git 저장소 **밖의 형제 디렉터리** `samplepcb-db-backups`다.

| 환경 | 기본 위치 |
|---|---|
| 현재 개발 PC | `D:/work/workspace_other/samplepcb-db-backups/` |
| 운영 배포 경로 | `/home/samplepcb/samplepcb-db-backups/` |

백업마다 `database.sql.gz`, `manifest.json`, 오류 로그가 생성된다. 스키마·데이터·뷰·루틴·이벤트·트리거와 `_prisma_migrations`를 포함한다. manifest에는 DB 이름·서버·시각·코드 참조·파일 크기·SHA-256·테이블 목록을 기록하며 비밀번호는 넣지 않는다. 코드 참조는 배포 스크립트 시작 시 HEAD 또는 백업 호출 시 HEAD의 기록이며, 복원할 코드 버전은 실제 이전 배포 버전으로 선택한다.

## 수동 백업·내용 확인

모노레포 디렉터리에서 실행한다.

```sh
pnpm --filter api db:snapshot backup
pnpm --filter api db:snapshot inspect "백업폴더의_절대경로"
```

백업은 서버의 MariaDB/MySQL 클라이언트를 사용한다. Linux에서는 `mariadb-dump`/`mysqldump`, Windows에서는 PATH 또는 XAMPP의 클라이언트를 찾는다. 암호는 인자에 노출하지 않고 실행 중 임시 옵션 파일로 전달한 뒤 제거한다. InnoDB는 단일 트랜잭션 스냅샷을 사용하고, 비트랜잭션 테이블이 있으면 dump의 테이블 잠금을 사용한다. DDL 배포 중 별도의 수동 스키마 변경을 병행하지 않는다.

## 운영 원복

**이 복원은 회원·주문을 포함한 DB 전체를 백업 시점으로 돌린다.** 운영 사용 기간에 생긴 데이터도 함께 되돌아간다. 결제 대행사의 실제 결제와 이미 발송한 메일은 취소되지 않는다. 외부 파일 저장소는 보존된다.

1. API·PHP 등 DB에 쓰는 서비스를 중지하거나 유지보수 상태로 둔다.
2. 아직 이 복원 도구가 있는 코드에서 아래 명령을 실행한다.
3. 복원이 끝나면 이전 코드와 그 버전의 Prisma 클라이언트·프런트 빌드를 배포한다.
4. 서버를 시작한다. 새 프로토타입 코드의 `pnpm dev`를 다시 켜면 migration이 재적용되므로 코드 원복 후 시작한다.

```sh
pnpm --filter api db:snapshot restore "/home/samplepcb/samplepcb-db-backups/선택한_백업폴더" --confirm-database samplepcb
```

`--confirm-database`는 현재 접속 DB 이름과 일치해야 한다. 도구는 먼저 백업 파일의 크기·SHA-256·DB 이름을 확인한다. 이어서 **복원 직전 현재 DB를 별도 백업**한 뒤 DB를 다시 만들고 선택한 SQL을 가져온다. 따라서 프로토타입에서 추가된 테이블과 migration 이력도 백업 시점으로 돌아간다. 가져오기 실패 시 직전 백업 재적용을 시도하며, 이 시도도 실패하면 백업 경로와 오류를 보고한다.

큰 BOM JSON·압축 바이너리는 SQL 한 문장이 수 MB가 될 수 있다. 복원 도구는 DB를 제거하기 전에 선택한 백업과 직전 상태 백업의 필요한 패킷 크기를 검사한다. 관리자 권한이 있으면 `max_allowed_packet`을 자동으로 늘리고, 권한이 없으면 데이터 변경 전에 중단하며 필요한 SQL을 알려준다. 이 경우 운영 DB의 관리자 접속에서 한도를 준비한 뒤 같은 복원 명령을 실행한다. 현재 개발 DB의 1MB 한도에서는 이 절차가 필요하다.

```sql
SET GLOBAL max_allowed_packet=268435456;
```

위 설정은 새 접속에 적용되는 서버 런타임 값이며 기능용 `.env` 설정이 아니다. 백업은 64KB 단위의 INSERT 묶음과 테이블별 트랜잭션으로 생성해 복원 부담을 줄인다.

접속 중인 서비스는 도구가 임의로 종료하지 않는다. 복원이 끝날 때까지 DB 쓰기를 중지해 두어야 한다. 복원 직전 백업도 삭제하지 않으며 필요하면 같은 명령으로 다시 적용할 수 있다.

## 검증

- 고유한 격리 테스트 DB에서 기존 행 수정·새 행 추가·새 테이블 생성 후 원래 스냅샷으로 복원했다.
- UTF-8 텍스트, 줄바꿈, 따옴표, 바이너리 값의 복원이 일치했다.
- SHA-256 불일치 백업은 DB 변경 전에 거부했다.
- 의도적으로 SQL 가져오기를 실패시켜 복원 직전 DB 자동 재적용을 검증했다.
- 시스템 DB(`mysql` 등)와 잘못된 DB 이름은 거부한다.
- 현재 규모의 실제 개발 DB 백업(압축 143,435,501바이트)을 별도 3344 서버에 복원했다. 기존 DB와 분리해 **151개 테이블 검사 정상**, 회원 6,387명·주문 16,349건·의뢰 3건을 확인했고 새 수행관리 테이블과 migration 이력이 사라진 백업 시점 상태를 확인했다.
- 기존 1MB 패킷 한도에서는 대형 BOM 행 복원이 불가능한 조건을 재현했다. 사전 검사가 DB 교체 전에 거부하는 것을 확인하고, 검증용 서버의 한도를 준비한 뒤 일반 DB 계정으로 전체 복원을 완료했다. 실제 개발 DB의 패킷 설정은 바꾸지 않았다.
