# 개발의뢰 수행관리 프로토타입

브랜치: `prototype/develop-workflow`, 기준 커밋: `845f69b4a`.
정본 업무 흐름은 [DEVELOP_FLOW.md](DEVELOP_FLOW.md), 화면 참고는 `.tmp/develop/Work flow.html`.

## 바로 보기 (현재 방식)

별도 기능용 환경변수 없이 `samplepcb-web-mono-app`에서 **`pnpm dev`**를 실행한다. API 시작 전에 필요한 마이그레이션을 확인하고, 미적용 변경이 있으면 DB 전체 스냅샷을 만든 뒤 `migrate deploy`로 적용한다. 이미 적용된 경우 백업·DDL 없이 바로 시작한다.

- 관리자: **https://local-web.samplepcb.co.kr/app/admin/develop** → 상단 **개발** → 진행현황 / 의뢰·검토 / 견적·계약 / 수행·일정 / 문서·승인 / 납품·검수 / 청구·결제 / 설정.
- 각 목록은 관련 상세 탭으로 바로 연결된다. 기존 의뢰 상세 주소도 유지하며, 검색·페이지·진입 메뉴와 선택 문서는 URL로 복구한다.
- 고객: **https://local-web.samplepcb.co.kr/develop/me** → 자신의 의뢰 선택.
- `prototype/develop-workflow`는 브랜치 이름이며 URL이 아니다. 이전 별도 시연 DB의 25번 의뢰는 통합 DB에서 사용하지 않는다.
- 수행관리 화면은 기본 제공한다. 의뢰별 실제 수행관리 시작은 담당자가 화면에서 선택한다.
- 운영은 평소의 `./deploy.sh 5`로 API·프런트·DB를 함께 배포한다. 2/5번의 DB 준비 단계에 자동 스냅샷이 포함되어 있다.

현재 사용자가 확정한 원복 방식은 **이전 코드 배포 + 배포 전 운영 DB 스냅샷 복원**이다. 상세 명령과 주의 범위는 [DB 스냅샷과 원복](db-snapshot-rollback.md)을 따른다.

## 개발 독립 메뉴 개편 (2026-09-09)

- 메뉴 정의·상세 진입·목록 복귀는 `apps/web/src/admin/develop-navigation.ts`, 업무 목록 화면은 `AdminDevelopWorkspace.vue`에 둔다. 기존 의뢰·검토와 설정 화면은 재사용한다.
- `GET /api/admin/develop/workspace`가 업무별 프로젝트 목록을 제공한다. 목록의 조건과 페이지 처리는 서버가 담당하며 상세 본문·문서 과거 버전은 목록에서 내려주지 않는다.
- 상세의 수행관리 영역은 착수·현황 / 일정 / 문서 / 납품으로 직접 접근한다. 계약서·납품서 유형 필터, 개별 문서 주소, 탭 이동 중 초안 보존, 화면 이탈 확인을 제공한다.
- 메뉴 개편에서 DB 스키마·데이터를 변경하지 않았다. PCB·BOM 주문과의 정식 데이터 연결은 후속 단계다.
- 검증: 새 목록 요약·권한·검색/페이지 테스트 7개 + 기존 수행관리 도메인 13개 통과. `pnpm -r typecheck`, 변경 파일 ESLint, 관리자/API 빌드, `git diff --check` 통과.
- 통합 도메인에서 실제 목록 API 6종·인증 차단·메뉴 8종을 확인했다. 문서 선택/새로고침/목록 복귀/미저장 내용 보호/모바일은 브라우저 안의 화면용 데이터로 검증하고 API 쓰기를 차단했다. 페이지 오류 0, 모바일 가로 넘침 없음. 증거는 `.tmp/develop-module/`에 보관한다.

## 확정 사항 (2026-09-09)

- 수락 견적과 지급 조건을 확인하고 필수자료 준비를 체크한 뒤 관리자가 착수한다.
- 계약 문서는 수락한 견적의 조건을 스냅샷으로 가져온다. 필요하면 날인본을 첨부한다.
- 승인이 필요한 작업만 문서와 연결한다. 승인 전에는 그 후속 작업을 시작할 수 없다.
- 기존 의뢰를 자동 전환하지 않고 의뢰별로 수행관리를 켠다.
- 작업 일정과 결제 마일스톤, 사전 AI 검토서와 중간 개발검토서는 구분한다.
- 공개본은 저장 중인 초안과 분리한다. 승인 대상은 특정 공개 버전이며 재발행 시 재승인이 필요하다.

진행 방식: 직접 구현. 계약 → 서버 상태 전이 → 공용 화면의 순차 의존과 운영 원복 조건을 함께 검증한다.

## 구현 구조

- 환경변수 기능 게이트를 제거했다. 개발 기동·운영 배포 과정에서 DB 준비가 완료되면 바로 제공한다.
- `sp_develop_workflow`: 의뢰별 적용 여부, 낙관적 잠금 revision, 버전이 붙은 수행관리 JSON.
- `sp_develop_workflow_audit`: 변경 주체·시각·작업의 추가 전용 이력.
- 기존 테이블의 컬럼·금액·상태 어휘를 변경하지 않는다. 필요한 정상 업무 전이는 기존 의뢰/이벤트에 기록한다.
- 문서는 유형별 필드·표·체크 목록을 계약 패키지에 정의한다. 작업본과 공개 버전은 별도이며 고객 응답은 공개 버전에 귀속한다.
- 공유 화면은 관리자 작성과 고객 열람·승인을 구분하고 서버에서 공개 범위를 다시 제한한다.
- 파일은 기존 `sp_file`에 `ref_type=sp_develop_workflow`로 연결한다. 공개 버전에 포함된 파일만 고객이 받는다. 납품 파일은 기존 잔금 잠금을 적용한다.
- 수동 청구(`manual`)는 상태 JSON의 `openedMilestoneIds`로 열고 기존 견적서의 결제 가능 표시·checkout과 연결한다. 금액은 기존 마일스톤을 그대로 쓴다.
- 고객 내 의뢰의 다음 할 일에 수행관리 승인 대기와 열린 수동 청구를 반영한다. 기존 중간 확인 요청도 이벤트별로 응답을 연결해 여러 요청 중 일부가 남아 있으면 표시한다.
- AI 문장 정리는 기존 `develop.dev-review` 연결·모델·사용 설정을 재사용한다. 고객 AI 동의를 확인하고 담당자가 입력한 텍스트만 전달한다. 결과는 편집용이며 자동 저장·공개·메일 발송을 하지 않는다.
- 메일은 최신 공개 버전만 선택하고 담당자가 본문을 확인한 뒤 발송한다. 발송 실패를 화면에 표시하고 메일 로그·수행관리 원장에 기록한다.

## 배포와 기능 원복

1. `pnpm dev`는 미적용 변경이 있을 때 전체 DB를 백업하고 마이그레이션한다. 운영 `deploy.sh` 2/5번은 매번 배포 전 DB를 백업하고 미적용 migration만 실행한다. 백업 실패 시 마이그레이션하지 않는다.
2. 운영 사용 후 되돌릴 때는 앱의 DB 쓰기를 중지하고 지정한 스냅샷을 복원한 뒤 이전 코드·Prisma 클라이언트·프런트를 배포한다. 새 환경변수를 설정할 필요가 없다.
3. 복원은 `_prisma_migrations`와 `g5_*`·`sp_*`를 포함한 **DB 전체 시점 복원**이다. 사용 중 추가된 테이블도 제거된다. 백업 이후 회원·주문·결제 기록도 돌아가므로 스냅샷 시각을 확인한다.
4. 복원 도구는 실행 직전 DB도 자동 백업한다. 선택한 스냅샷의 가져오기가 실패하면 그 직전 상태 재적용을 시도한다.
5. 문서 기록·첨부를 별도로 인계하려면 복원 전 `기록 내보내기`와 다운로드를 사용한다. DB 복원은 실제 결제나 발송 메일을 취소하지 않으며 외부 파일 저장소를 삭제하지 않는다.

의뢰별 수행관리 중단은 기존처럼 데이터를 보존한다. 브라우저에 새 프런트가 남아 있고 API만 먼저 이전 버전으로 돌아가 404가 나도 수행관리는 숨겨진다.

## 검증 원칙

- 기능 테스트는 격리 DB에서 검증한다. 현재 통합 개발 DB에는 사용자 요청에 따라 스냅샷을 확보하고 수행관리 마이그레이션을 적용했다. 기존 의뢰를 자동 전환하지 않는다.
- 메일·파일서버·AI는 테스트 대역으로 격리한다. 테스트가 실제 고객 메일·주문을 만들지 않는다.
- 타입 검사·린트·도메인/라우트 테스트, 실제 브라우저의 관리자/고객 화면을 확인한다.
- 운영 배포는 구현·검증 결과와 구체적인 배포/원복 절차가 준비된 뒤 별도 단계에서 진행한다.

## 초기 격리 검증 환경과 결과

로컬 원본 MySQL(3306)이 중지된 상태여서 원본을 복구하거나 시작하지 않았다. `C:/xampp/mysql/bin`의 MariaDB 실행 파일로 **별도 데이터 디렉터리** `.tmp/develop-workflow/mariadb-data`와 **127.0.0.1:3340**에 인스턴스를 초기화했다. 원본 데이터를 복사한 DB가 아니라, 기준 커밋의 Prisma 스키마와 그누보드 코어 SQL로 만든 합성 시험 DB다.

- DB: `samplepcb_develop_workflow_proto`. 기존 스키마 생성 후 신규 migration을 `prisma migrate deploy`로 실제 적용했다.
- 운영 DB·원본 로컬 DB·라이브 nginx 설정은 변경하지 않았다.
- API 3339, 관리자 Vite 5183, 고객 Vite 5182. Windows의 5184~5283 예약 범위를 피했다.
- 실행 파일: `apps/api/src/scripts/preview-develop-workflow.ts`. 격리 DB/포트와 `WORKFLOW_PREVIEW=1`을 검사하고 127.0.0.1에서만 데모 인증을 제공한다. 운영 `server.ts`에는 등록하지 않는다.
- 파일 서버 대역 3449는 `.tmp/develop-workflow/files`에 저장한다. SMTP 대역 2529는 `.tmp/develop-workflow/mail`에만 저장하고 외부로 발송하지 않는다.
- `.tmp/develop-workflow/prototype.env`와 `web.env`는 시연 전용이며 Git에 넣지 않는다. 관리자 인증 프록시만 `web.env`의 `/admin-auth` 경로를 쓴다.

재실행(해당 앱 디렉터리에서):


예전 Prisma 스키마로 클라이언트를 다시 생성할 때는 모노레포 안의 임시 경로와 `PRISMA_GENERATE_SKIP_AUTOINSTALL=1`을 사용한다. 별도 프로젝트 루트에서 자동 설치를 유도하지 않는다. 이번 비교용 산출물은 `.tmp/develop-workflow/baseline-client`와 `rollback-check.json`에 있다.

실 PG 결제, 외부 LLM의 실제 응답 품질, 운영 파일서버의 업로드 수용 및 실제 고객 메일 배달은 이번 격리 검증에 포함하지 않았다. 운영 첫 적용은 시험 의뢰에서 이 연동들을 확인한 뒤 확대한다.

위 별도 포트 시연 환경은 초기 격리 검증용 기록이다. 현재 확인 주소는 맨 위의 통합 도메인이다.
