**현재는 공존 구현을 완료했다. [사용 경로·분리 방식·검증](develop-prototypes.md)을 참고한다. 아래는 구현 전 검토 기록이다.**

검토일: 2026-09-09. 공존용 작업 브랜치: `prototype/develop-g-c`.

## 결론과 현재 작업 상태

한 관리자 화면에 `통합 | PCB | BOM | 개발(G) | 개발(C)`를 함께 제공할 수 있다. 다만 메뉴 이름 변경만으로는 두 구현이 분리되지 않는다. 경로·API 응답·브라우저 캐시와 의뢰의 업무 처리 주체를 분리해야 한다.

- G 기준: `prototype/develop-workflow`, `91a0ddfef`. 새 작업 브랜치에서 상단 표시 이름만 `개발(G)`로 변경했다. 기존 경로·업무 로직·DB는 그대로다.
- C 기준: `origin/feat/develop-workflow-docs`, `67c70a183`. `.tmp/develop-c-review/`에 별도 Git worktree로 체크아웃하고 표시 이름만 `개발(C)`로 변경했다. 해당 변경은 검토 worktree에만 있다.
- 공통 조상: `845f69b4a`. 실제 병합 없이 `git merge-tree --write-tree --name-only`로 확인한 텍스트 충돌은 **13개 파일**이다.
- C 서버 실행·의존성 설치·Prisma 생성·DB migration·병합·커밋·push는 이번 검토에서 수행하지 않았다. 두 메뉴의 동시 실행은 아직 구현되지 않았다.

두 쪽의 추가 테이블 이름과 migration 디렉터리 이름은 겹치지 않는다. Prisma 모델은 둘을 모두 포함하도록 구성할 수 있으며, 기존 G migration을 수정할 필요는 없다. 단순 병합 시 schema.prisma 충돌은 별도로 해결해야 한다.

## 이름 변경 외에 필요한 분리

1. **관리자 경로와 컴포넌트**: 양쪽 모두 `/app/admin/develop`, `admin-develop-*`, `AdminDevelopRequestDetail.vue`, 같은 메뉴 키를 사용한다. G의 기존 경로는 유지하고 C를 `/app/admin/develop-c`와 `admin-develop-c-*`로 옮기는 방식을 추천한다. 모듈 판정은 C를 먼저 확인해야 G 접두 매칭에 잡히지 않는다. C의 페이지·훅·번역 키도 별도 범위로 둔다.
2. **API와 응답 계약**: 기존 목록·상세 경로가 같다. C는 목록에 필수 `ops`·`signals`, 상세에 `documents`·`progress`, 상태 탭에 `intake`·`contract`를 추가했다. G의 계약 위에 그대로 덮으면 G 목록 집계도 영향을 받는다. C용 `/api/admin/develop-c`·`/api/develop-c`와 별도 계약을 두고 기존 인증·파일 전송 기반만 공유하는 방식을 추천한다.
3. **브라우저 캐시**: 두 구현 모두 `['admin', 'develop', ...]`를 쓴다. C는 `develop-c` 키를 사용해 서로 다른 응답과 무효화가 섞이지 않게 한다. 고객 상세·인쇄·메일 링크도 같은 원칙으로 분리한다.
4. **의뢰와 결제 상태**: 두 구현 모두 같은 `sp_develop_request`, 견적·마일스톤·이벤트를 변경한다. 추가 문서 테이블이 달라도 같은 의뢰 번호를 양쪽에서 수정하면 독립 시험이 아니다. 의뢰마다 G/C 소속을 정하고 서버의 조회·작성·파일·결제·자동 검수 경로에서 소속을 확인해야 한다. 기존 의뢰는 G로 유지하고 C 시험 의뢰만 명시적으로 배정한다. 구현 시 별도 매핑 테이블 같은 저장 장치가 필요하다.
5. **개발 설정**: 두 쪽의 개발 설정은 기존 단일 `sp_develop_settings`를 공유한다. C에서 기본 마일스톤·조건을 바꾸면 G에도 영향을 준다. 독립 비교를 위해 C의 개발 업무 설정도 별도 저장 대상으로 분리한다. 회원·인증과 공통 인프라 설정은 공유할 수 있다.

구체적인 간섭 사례: C 고객의 납품확인 승인은 기존 의뢰를 `completed`로 바꾼다. G는 완료된 의뢰를 읽을 때 G의 납품 공개본 응답도 동기화한다. 같은 의뢰를 사용하면 C에서 한 승인 때문에 G에서도 완료/승인 상태가 바뀔 수 있다. C의 변경요청 승인도 공용 견적 테이블에 새 견적과 결제 계획을 생성한다.

## 추천하는 비교 방식

- 하나의 앱·배포와 같은 로그인 아래에 두 메뉴를 둔다. G 업무 규칙과 C 업무 규칙은 각각 유지한다.
- 동일한 요구사항을 비교하려면 **G용 의뢰와 C용 의뢰를 한 쌍으로 만든다**. 입력 내용만 복제하고 결제 식별자·승인·발송 이력은 독립적으로 유지한다.
- 고객도 해당 의뢰의 소속에 맞는 상세·문서·인쇄 경로로 들어간다. 관리자 메뉴만 나누고 고객 상세에서 두 응답 체계를 합치면 비교가 흐려진다.
- 선택한 한 프로토타입을 추후 제외할 때는 해당 메뉴·라우트를 제거하고 시험 데이터를 보관한다. 원본 두 브랜치는 보존한다.

## DB 적용과 원복

G의 자동 백업·DB 준비 절차를 공존 브랜치의 배포 기반으로 유지한다. C의 dev 스크립트로 덮어쓰면 G의 기동 전 자동 백업·migration 단계가 사라지므로 package.json 충돌을 그대로 C 쪽으로 해결하지 않는다.

C의 `down.sql`은 C 문서·업무표와 일부 첨부/이벤트/AI 이력을 제거하는 도구다. C 시험 중 바뀐 기존 의뢰 상태나 생성된 변경 견적·결제 계획을 전부 되돌리는 도구는 아니다. C 문서의 기존 원복 예시도 main 체크아웃 뒤 사라진 C 전용 down.sql 경로를 참조하므로 공존 배포 절차로 그대로 재사용하지 않는다.

운영 전체를 시험 전으로 되돌릴 때는 기존 [DB 스냅샷과 원복](db-snapshot-rollback.md)을 사용한다. 같은 DB를 사용하면 전체 스냅샷 복원은 G와 C 양쪽 및 이후 회원·주문을 함께 되돌린다.
